>
> **v2 수정**: 초판은 "기술 수준"으로 페르소나를 나누고, 그 기준으로
> 사용 방식을 `python main.py --request "..." --continuous --interval 3`
> 같은 CLI 플래그로 가정했음. 틀림 — 2026년에 agent 서비스를 플래그로
> 쓰는 사람은 개발자든 아니든 없음. 다들 챗박스에 "이거 조사해줘" 치고
> 결과 받는 걸 기대함. 기술 수준이 아니라 **목적/관계(최종 사용자 vs
> 이 시스템을 코드/인프라로 다루는 사람)**로 다시 나눔.
>
> **v3 수정**: v2에서 "페르소나 2/3은 코드를 보는 사람이니 CLI 가정이
> 맞는 축"이라고 썼는데 이것도 틀림. `python main.py --request ...`는
> dev entrypoint고, 이미 잡혀있던 규칙이 "이걸 직접 치지 말고 설치된
> `sparkleforge`/`sparkle` 커맨드를 써라"였음 — 즉 이 실행 방식 자체를
> 모든 사용자가(개발자 포함) 혐오함. 기술 수준과 무관하게 `main.py`
> 직접 호출은 셋 다에서 나쁜 인터페이스.
>
> **v4 수정**: v3에서 정상 인터페이스를 "설치된 커맨드 / 챗 / SDK·API"
> 세 갈래로 나눴는데 과설계. 정답은 하나 — `sparkleforge`를 치면 그
> 자체로 Claude Code/Codex CLI처럼 **인터랙티브 에이전트 세션**이
> 열리고, 그 안에서 자연어로 대화하며 리서치가 진행됨. "챗 인터페이스"
> 따로, "설치된 커맨드" 따로가 아니라 설치된 커맨드가 곧 챗 인터페이스.
>
> **v5 수정 (코드 확인 후, v4까지 전제가 틀렸음)**: v1~v4 전부 "CLI를
> 인터랙티브 세션으로 바꿔야 한다"를 미구현 갭으로 취급했는데, 실제
> 코드(`main.py:792-796`, `src/cli/repl_cli.py`)를 보니 **이미 구현되어
> 있음**. 인자 없이 `sparkleforge`만 치면 자동으로 REPL 진입 — 정확히
> Claude Code/Codex 패턴. 헤드리스 자동화용 `--prompt` 플래그(`claude
> -p`에 대응)도 이미 있음(`main.py:700`). 근거는 `README.md`의 Quick
> Start 예제가 여태 `python main.py --request ...`/`streamlit run
> ...`만 보여줬다는 것뿐이었음 — 즉 **코드가 아니라 문서가 오래됨**.
> 아래 페르소나 1/2 항목 중 "필요한 것"으로 CLI 세션·헤드리스 모드를
> 요구한 부분은 이미 해결된 상태로 정정. 진짜 남은 갭은 (a) README
> 수정(이번 PR), (b) 모바일/웹(#1136, ideation만 닫히고 구현 이슈 없음).

## 1. 리서치 요청자 — "그냥 물어보고 결과 받는 사람"

기술 수준 무관. 개발자든 아니든 이 시스템에 대해 원하는 인터페이스는
동일함 — 챗박스 하나. 차이는 "얼마나 자주/깊게 쓰는가" 정도지 CLI를
아느냐가 아님.

- **컨텍스트**: "이 주제 조사해줘" 치고 결과 기다림. 가끔은 며칠짜리
  24x7 모니터링을 걸어두고 싶어함(`--continuous` 개념 자체는 유효한
  기능, 문제는 그걸 플래그로 노출하는 방식).
- **목표**: 조사 요청 → 진행상황 확인 → 완료 리포트 확인. 이 세 단계가
  전부 대화형으로 되길 원함.
- **페인포인트**: 실제로는 `sparkleforge` 인터랙티브 세션이 이미 있는데,
  `README.md`가 여태 `python main.py --request ...`/`streamlit run
  ...`만 보여줘서 이 사람이 그 존재를 알 방법이 없음. 문서가 안 좋은
  진입점을 정답인 것처럼 광고하는 셈.
- **필요한 것 (v5 정정)**: (1) `sparkleforge` REPL — **이미 있음**,
  README만 고치면 됨(이번 PR). (2) PC 앞에 없을 때 쓰는 모바일/웹
  (#1136) — 이건 진짜 안 만들어져 있음. CLI 세션에 원격으로 붙는
  창구가 아니라 별도 표면이고, run-trigger/status/report-read를 API로
  노출해야 만들 수 있음. ideation 이슈(#1136)는 닫혔지만 구현 이슈가
  없음 — 여기가 진짜 남은 작업.
- **한 줄**: "조사해달라고 말했지, 명령어 외우겠다고 한 적 없음." (이미
  그렇게 돼있다는 걸 아무도 안 알려줬을 뿐.)

## 2. 에이전트 플랫폼 엔지니어 — "Anvil을 인프라로 쓰는 사람"

최종 사용자가 아니라 이 시스템 위에 자기 걸 얹는 사람. 탐색할 땐 이
사람도 그냥 `sparkleforge` 인터랙티브 세션 씀. 자기 파이프라인에 자동화로
묶을 땐 `sparkleforge --prompt "..."`(헤드리스, `claude -p`에 대응) —
**이것도 이미 있음**(`main.py:700`). 남은 건 이걸 라이브러리 레벨 SDK로
쓸 수 있게 노출하는 것(현재는 CLI 프로세스 스폰만 가능, in-process
import는 안 됨) 정도.

- **컨텍스트**: 자기 에이전트 스택 위에 Anvil의 observe/actuate/guard
  plane을 얹으려는 사람. `capability_manager`, `sandbox_executor`,
  `action_journal` 같은 걸 직접 코드로 봄.
- **목표**: 에이전트 행동을 감사 가능하게, 권한을 통제 가능하게.
- **페인포인트**: 컴포넌트는 있는데 실제 실행 경로에서 안 불리는 경우
  (`ANVIL_PLAN.md` §3의 AnomalyDetector 사례). 있는 줄 알았던 안전장치가
  실제로는 배선 안 됨.
- **필요한 것**: "존재함"과 "실제 호출됨"을 구분해서 보여주는 문서/테스트
  (`test_os_plane_integrity.py` 같은 것). Τ(syscall 경계), Π(VFS 통합)
  로드맵의 실배선 여부. 헤드리스 CLI(`--prompt`)는 이미 있으니, 남은 건
  같은 기능을 서브프로세스 스폰 없이 라이브러리로 import해서 쓸 수 있는
  SDK 노출(확인 결과 현재 없음) — 이게 이 페르소나가 실제로 통합
  작업을 시작할 수 있는 전제조건.
- **한 줄**: "모듈 있다고 안심 안 함. 콜 그래프로 증명해라."

## 3. OSS 메인테이너 — "Nightwelding 결과물을 리뷰하는 사람"

인터페이스는 GitHub PR 화면과 CI 로그. 로컬 재현이 필요하면 설치된
`sparkleforge` 커맨드로 하지, 저장소 clone해서 `main.py` 돌리는 거
아님.

- **컨텍스트**: SparkleForge 저장소 자체 또는 자기 저장소에 Nightwelding
  자동수정 파이프라인 붙임. 매일 올라오는 Draft PR 리뷰.
- **목표**: 자동 수정이 진짜 근본 원인을 고치는지, 머지 전에 걸러내기.
- **페인포인트**: 재현 테스트가 허술하면 증상만 고치고 넘어감. 자동
  머지되면 신뢰 못함 (`CLAUDE.md`: 머지는 사람이 명시적으로 지시할 때만).
- **필요한 것**: 재현 테스트 품질 게이트(서브디렉토리 회피 등 최근 수정
  사례처럼), 에러가 요약이 아니라 job log에 그대로 남는 것.
- **한 줄**: "고쳤다는 주장 말고, 실패하던 테스트가 통과하는 걸 보여줘라."

`src/cli/repl_cli.py`가 이미 그 기능이고, 헤드리스용 `--prompt`도
`main.py:700`에 이미 있음. **문제는 코드가 아니라 `README.md`가 그
사실을 안 보여준 것** — Quick Start가 여태 `python main.py
--request ...`/`streamlit run ...`만 예시로 들었음.

- **SDK 노출**(미해결, 별도 작업): 페르소나 2가 자기 파이프라인에 이
