## ⚠️ 냉혹한 코드 퀄리티 비평 (Critical Review)

> [!WARNING]
> 아래 비평은 작업물에 대한 관용이나 칭찬을 배제한 시스템 아키텍트의 엄격한 관점입니다.

제시된 커밋과 변경 사항에 대한 아키텍트로서의 비판적 평가입니다.

### 1. 기술 부채 및 설계 결함 (Technical Debt & Design Flaws)

*   **`VerificationNode`의 무책임한 초기화:** `VerificationNode.__init__`에서 `_mode_controller`를 `None`으로 강제 초기화한 것은 전형적인 '땜질식 처방(Patchwork)'입니다. 의존성 주입(Dependency Injection)을 통해 명확한 인터페이스를 강제하는 대신, 런타임에 `None` 체크를 강요하는 구조를 만들었습니다. 이는 향후 `ModeController`가 필요한 시점에 `AttributeError`나 `NoneType` 오류를 유발할 잠재적 시한폭탄입니다.
*   **테스트 스위트의 '사후 약방문':** `tests/test_os_plane_integrity.py`가 CI에 추가된 것은 다행이나, 그동안 이 핵심 경로가 CI에서 제외되어 있었다는 사실 자체가 시스템의 신뢰성을 심각하게 훼손합니다. " tribal knowledge(구전 지식)"에 의존했다는 고백은 아키텍처 거버넌스의 실패를 의미합니다.
*   **`todo-issue-sync.yml`의 복잡도:** `scripts/collect_todos.py`를 통해 이슈를 자동 생성하는 로직을 워크플로우 내부에 파이썬 인라인 스크립트로 구현했습니다. 이는 유지보수가 극도로 어렵습니다. 이슈 생성 로직이 변경될 때마다 YAML 파일과 파이썬 코드를 동시에 수정해야 하며, 이는 디버깅을 악몽으로 만듭니다.

### 2. 레이스 컨디션 및 안정성 (Race Conditions & Stability)

*   **`swebench-weekly.yml`의 동시성 제어:** `concurrency` 그룹을 `swebench-lite`로 설정했으나, `cancel-in-progress: false`로 설정되어 있습니다. 만약 수동 트리거와 스케줄러가 겹칠 경우, 동일한 리포지토리에 대해 여러 번의 SWE-bench 실행이 시도될 수 있습니다. 이는 리소스 낭비뿐만 아니라, `docs/SWEBENCH_REPORT.md`에 대한 쓰기 작업 시 Git 충돌을 유발할 가능성이 매우 높습니다.
*   **Git 작업의 원자성 결여:** `record-report` 작업에서 `git push`를 수행하기 전 `git pull --rebase`를 수행하지 않습니다. 여러 워크플로우가 동시에 실행되거나, 다른 PR이 병합된 직후라면 `git push`는 실패할 것이며, 이는 자동화 파이프라인의 중단을 초래합니다.

### 3. 에지 케이스 및 보안 (Edge Cases & Security)

*   **PAT(Personal Access Token) 의존성:** `todo-issue-sync.yml`에서 PAT가 없으면 실패하도록 강제했습니다. 이는 로컬 개발 환경이나 포크된 리포지토리에서 테스트를 불가능하게 만듭니다. 환경 변수 체크를 통해 우아하게(gracefully) 기능을 비활성화하는 대신, 파이프라인 자체를 'Hard-fail' 시키는 것은 CI/CD 설계의 유연성을 떨어뜨립니다.
*   **SWE-bench 실행 시간:** `timeout-minutes: 300`은 5시간입니다. 이는 GitHub Actions 비용을 급격히 상승시킵니다. 만약 `psf/requests` 외에 다른 리포지토리로 확장할 경우, 이 시간은 기하급수적으로 늘어날 것이며, 현재의 단일 워크플로우 구조로는 확장성(Scalability)이 전혀 고려되지 않았습니다.

### 4. 개선 권고 사항 (Actionable Recommendations)

1.  **의존성 주입 리팩토링:** `VerificationNode`에서 `_mode_controller`를 `None`으로 두지 말고, `Optional[ModeController]` 타입을 명시하고 이를 사용하는 모든 메서드에서 명확한 상태 머신(State Machine) 패턴을 적용하십시오.
2.  **Git 작업의 안전성 강화:** `record-report` 단계에서 `git push`를 수행하기 전에 반드시 `git fetch`와 `git rebase origin/main`을 수행하여 충돌을 방지하는 로직을 추가하십시오.
3.  **워크플로우 모듈화:** `todo-issue-sync.yml` 내의 파이썬 코드를 별도의 `scripts/` 디렉토리로 완전히 분리하고, 워크플로우는 이를 호출만 하도록 변경하십시오.
4.  **비용 최적화:** SWE-bench 실행 시 `max_workers`를 1로 고정한 것은 안전하지만, 리포지토리 확장 시에는 매트릭스 전략(Matrix Strategy)을 사용하여 병렬 처리를 도입하고, 전체 실행 시간을 단축할 수 있는 아키텍처를 설계하십시오.

**총평:** "보여주기식" 무결성 증명(Integrity Proof)을 위해 CI를 보강한 점은 인정하나, 그 과정에서 도입된 복잡한 자동화 스크립트들이 새로운 기술 부채를 양산하고 있습니다. 특히 Git 기반의 자동 기록 방식은 확장성이 낮고 충돌 위험이 큽니다. 다음 단계에서는 **'자동화의 자동화'**가 가져올 운영 비용을 심각하게 고려하십시오.
